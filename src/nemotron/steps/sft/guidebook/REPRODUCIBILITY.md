## Quick start

One arm, end to end — the recommended recipe for a new target language:

```bash
# 1. generate persona-grounded MCQ data (English + target)
nemotron steps run sdg/persona_mcq        -c default  pipeline.experiment_name=<run>

# 2. pack to fixed-length sequences for Megatron-Bridge
nemotron steps run data_prep/sft_packing  -c <pack-config>  -b <profile>

# 3. fine-tune
nemotron steps run sft/megatron_bridge    -c <sft-config>   -b <profile>

# 4. serve each saved checkpoint and evaluate
```

Each arm here is **500 iterations at a 32,768-token sequence length and a global
batch of 64** — 2,097,152 tokens per iteration, ≈1.05 B tokens per arm — with a
checkpoint every 50 iterations.

## Hardware

**Training (all SFT arms)**

| Item | Value |
|---|---|
| Nodes | 4 |
| GPUs per node | 8 × NVIDIA H100 80GB SXM |
| Total GPUs | 32 |
| Precision | BF16 |
| Storage | shared POSIX filesystem, readable from every node |

The 32-GPU layout follows from the parallelism: tensor-parallel 8 × data-parallel 4,
with expert-parallel 8 over the MoE layers (PP 1, CP 1, ETP 1). Gradient
accumulation is therefore `64 / (1 × 4) = 16` micro-batches per step.

**Evaluation / serving**

Checkpoints are served over HTTP and evaluated through `nemo-evaluator`. Serving
parallelism must match training.

> [!IMPORTANT]
> **Packed sequences require `micro_batch_size: 1`.** The packing step already
> concatenates samples up to `packed_sequence_size`, so a larger micro-batch
> multiplies the real sequence length and will OOM.

## Data

### Training data

Generated by [`sdg/persona_mcq`](../../sdg/persona_mcq/README.md) — see
[section 2 of the guidebook](./README.md#2-curating-the-adaptation-data) for the
rationale behind each gate.

| Item | Value |
|---|---|
| Personas | Nemotron Personas India — locales `en_IN`, `hi_Deva_IN` |
| Question models | Qwen3.5-122B-A10B, gpt-oss-120b, gemma-4-31B-it |
| Answer models | the same three, each answering every question |
| Agreement gate | `unanimous` — all three teachers must agree |
| Lexical dedup | MinHash/LSH, threshold 0.80, 4-shingles, 128 permutations, 16 bands |
| Semantic dedup | `intfloat/multilingual-e5-large`, cosine 0.965, greedy |
| Script gate | assistant Devanagari fraction 0.00–0.15 (English), 0.70–1.00 (Hindi) |
| Reasoning blend | `reasoning_off_fraction: 0.10` — 90:10 on:off |
| Answer variant | `full`, boxed final answer |
| Volume | 50,000 per language (100k total) before packing |
| Seed | 42 |

The Malayalam runs use the same pipeline with the `ml` locale and a boxed
variant tuned for that script (`boxed_en50_ml100`).

Two auxiliary packs appear in the guidebook:

| Pack | Contents | Used in |
|---|---|---|
| IF replay | 20k English instruction-following samples | [§6](./README.md#6-replay-english-alongside-the-target-data) |
| Translation | bidirectional en↔target pairs (Updesh) | [§7](./README.md#7-measure-language-fidelity-not-just-accuracy) |

### Base checkpoints

| Base | Identifier |
|---|---|
| Released SFT+RL | `nvidia/NVIDIA-Nemotron-3-Nano-30B-A3B-BF16` |
| Pre-RL SFT-only | internal Nemotron-3-Nano SFT checkpoint, iteration 13,600 |

> [!NOTE]
> The pre-RL checkpoint is **internal and not publicly available**. Every result
> in the guidebook that depends on it is labelled "pre-RL". The recipe reproduces

## Pipeline

```bash
# generate the adaptation data
nemotron steps run sdg/persona_mcq        -c default   pipeline.experiment_name=<run>

# pack JSONL -> fixed-length packed parquet
nemotron steps run data_prep/sft_packing  -c <pack-config>  -b <profile>

# fine-tune from packed parquet
nemotron steps run sft/megatron_bridge    -c <sft-config>   -b <profile>
```

`<profile>` is a scheduler profile from your `env.toml`.

Packing is required for the Megatron-Bridge backend and must use the **same**
`packed_sequence_size` as `dataset.seq_length` in the SFT config. The AutoModel
backend reads JSONL directly and skips this step; see
[the backend guide](../guide.md).

Pinned dependencies at the time these runs were produced:

| Component | Revision |
|---|---|
| Megatron-LM | `bbbedbb9f53343762e4dc70abc771b813a83d817` |
| Megatron-Bridge | branch `romeyn/parquet-sequence-pack` |

## Hyperparameters

Shared by every full-SFT arm:

| Group | Setting | Value |
|---|---|---|
| Recipe | | `megatron.bridge.recipes.nemotronh.nemotron_3_nano.nemotron_3_nano_finetune_config` |
| | `packed_sequence` | `true` |
| | `peft` | `null` (full-parameter) |
| Parallelism | tensor / pipeline / context | 8 / 1 / 1 |
| | expert / expert-tensor | 8 / 1 |
| | sequence parallel | on |
| Batch | sequence length | 32,768 |
| | global / micro batch | 64 / 1 |
| | tokens per iteration | 2,097,152 |
| Optimizer | lr / min lr | 1.0e-5 / 1.0e-5 |
| | weight decay | 0.01 (constant) |
| Schedule | decay style | **constant** |
| | warmup | 5% of `train_iters` |
| Loss | `calculate_per_token_loss` | `true` — correct for packed varlen |
| Misc | seed | 42 |

`lr == min_lr` with `lr_decay_style: constant` keeps the rate flat after warmup.
That is deliberate: under a cosine schedule the rate at step *k* depends on the
total `train_iters`, so intermediate checkpoints are partially-decayed runs and
are not comparable to each other. See
[§4](./README.md#4-learning-rate-and-schedule).

**LoRA arms** ([§8](./README.md#8-use-full-parameter-sft)) change only:

| Setting | Value |
|---|---|
| `peft.type` | `lora` |
| `dim` / `alpha` / `dropout` | 16 / 32 / 0.0 |
| `target_modules` | `linear_qkv`, `linear_proj`, `linear_fc1`, `linear_fc2` |
| lr | **1.0e-4** (an adapter barely moves at 1e-5) |

## Cost and runtime

> [!NOTE]
> Wall-clock and GPU-hours for these runs were **not recorded in a form we can
> publish** — the training runs did not land in the tracked W&B project. The
> token budgets below are exact and derived from the configuration; plan from
> your own measured step time on the shape above.

| Arm length | Tokens per iteration | Total tokens |
|---|--:|--:|
| 500 iterations | 2,097,152 | ≈1.05 B |
| 1000 iterations | 2,097,152 | ≈2.10 B |

The full study behind this guidebook trained and evaluated **307 checkpoints** —
more experiments than are published here, since not every arm produced a
recommendation worth shipping. Each checkpoint was evaluated
on four benchmarks across three languages and two reasoning modes.
**Evaluation, not training, was the dominant cost**: that is 20 benchmark ×
language × mode cells per checkpoint — MILU, GSM8K-Indic and IndicIFEval at
3 languages × 2 modes each, plus IndiVibe at 2 modes — with every generative
benchmark decoding at up to 16,384 new tokens. Budget for it explicitly; it is
easy to plan the training and be surprised by the evaluation.

## Evaluation

Checkpoints are served over HTTP and evaluated with `nemo-evaluator run_eval`
in `chat` mode.

| Benchmark | Dataset | n | Measures |
|---|---|--:|---|
| MILU | `ai4bharat/MILU`, test | 13,535 en / 14,831 hi / 4,321 ml | knowledge (MCQ) |
| GSM8K-Indic | `sarvamai/gsm8k-indic` | 1,319 | grade-school maths |
| IndicIFEval | `AI4Bharat/IndicIFEval`, `trans_*` only | 490 | instruction following |
| IndiVibe | `sarvamai/indivibe`, Hindi-native | 110 | open-ended generation |

Standard errors: MILU 0.4pp (en/hi) and 0.76pp (ml), GSM8K-Indic 1.3pp,
IndicIFEval 2.4pp, IndiVibe 4.8pp.

**Decoding**, applied identically to every checkpoint:

| Mode | Settings |
|---|---|
| Reasoning **on** | `temperature=1.0`, `top_p=1.0` |
| Reasoning **off** | `temperature=0.0`, `top_p=1.0`, `chat_template_kwargs.enable_thinking=false` |
| Both | `max_new_tokens=16384` |

**IndiVibe** is a pairwise win-rate against **each arm's own base model**, judged
by an LLM using IndiVibe's own judge templates verbatim. Candidate and baseline
positions are swapped per prompt and de-swapped when parsing, which controls
position bias within a single call. 50 means no change from the base.

**Script fidelity** is measured separately from accuracy: for each generative
benchmark, the share of responses whose dominant script is the one the question
was asked in. Digits and punctuation are ignored; responses with no letters at
all are excluded from the denominator rather than counted either way.

> [!IMPORTANT]
> Two evaluation details that changed conclusions in this study:
>
> - **Drop rows whose `status` is not `scored`.** These are endpoint failures,
>   not wrong answers, and counting them as incorrect understates the model.
> - **Use only the `trans_*` IndicIFEval subsets.** The natively-authored
>   `ground_*` subsets ship `keywords:frequency` constraints with
>   `relation: null`, so "at least N" versus "less than N" is decided at scoring
>   time and an off-language model can satisfy them for free.

## Adapting to a new language or domain

The pipeline is language- and domain-agnostic; four things change.

1. **Personas and locale** — point `sdg/persona_mcq` at the locales for your
   target. The gates (unanimous agreement, both dedup stages, the script
   fraction) stay as given.
2. **Data shape** — MCQ is one example. A coding-assistant or support-agent
   adaptation generates a different artefact through the same gates. Keep the
   50/50 English:target split and the 90:10 reasoning blend.
3. **Volume and iterations** — start at 50k–100k total samples. `train_iters`
   follows from your pack size and the number of epochs you want; keep the
   checkpoint cadence identical across arms you intend to compare.
4. **Benchmarks** — substitute a target-domain benchmark for MILU, and keep an
   English retention set unchanged so retention stays comparable across arms.

Everything else — parallelism, batch, learning rate, schedule, the replay
recipe — transfers unchanged and is the recommended starting point.

## What to record

Config name, code revision, base checkpoint, sample counts and language split,
reasoning-on:off fraction, `train_iters`, warmup, checkpoint cadence, checkpoint
path, decoding settings, and evaluation harness. Scores are harness-dependent:
never compare a number produced by one harness against a number produced by
another.
